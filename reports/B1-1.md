## 1. What Agent B3 must call

Three methods on the `Editor` wasm handle. All are pure reads — no mutation, no re-generation.

```ts
editor.quantities()                      // → Quantities  (the whole surface)
editor.ground_truth_json(planLabels)     // → string, write straight to out/ground-truth.json
editor.wall_types()                      // → per-wall classification, for the PLAN RENDERER
```

### `quantities()`

```ts
{
  sqfPerM2: 10.764,          // exact, per orchestrator ruling 3
  wallHeightM: 2.6,          // the ONE height assumption (see §4)
  floorAreaM2: number,       // traced plate area
  walls: [{                  // ALWAYS all 6 types, legend order, zero-length included
    wallType: 'Drywall' | 'HalfDrywall' | 'Glass' | 'Core'
            | 'PerimeterWindows' | 'PerimeterWall',
    label: string,           // 'Drywall' | 'Half Drywall' | … — the General!J* Material Name
    lengthM: number,         // total centreline run
    heightM: number,         // 2.6, except Half Drywall = length-weighted mean of its own heights
    areaM2: number,          // lengthM × heightM
    segments: number,        // modelled Wall count (Core may be 0 — see §3)
  }],
  doors: [{ doorType: 'Glass'|'Solid', label, count, totalWidthM }],  // ALWAYS both
  doorCount: number,         // exact
  doorTotalWidthM: number,   // the legend's Door_length
  rooms: [{
    roomId: number,          // zone id — unique by construction
    name: string,            // zone label
    zoneType: 'Workspace' | 'Meeting' | …,
    spaceType: string,       // human label, e.g. 'Meeting Room'
    areaM2: number, areaSqf: number,
    headcount: number,       // measured seats (non-reference Desk + Chair inside the zone)
    capacity: number,        // area rule-of-thumb, kept alongside — never substituted for headcount
  }],
}
```

**Wiring notes for B3.**
* `General!J9:J14` should list **all six** `walls[].label` values in the order given. G3 fails both
  directions (a workbook type missing from ground truth, *and* a ground-truth type missing from the
  workbook), so the row set has to be exactly this. `Half Drywall` will normally be `0.00` — that is
  the honest number, and the reference workbook's own plan has zero of it too.
* `General!L{r}` = `walls[].lengthM`. For a `length × height` area formula use `walls[].heightM`,
  **not** a hard-coded 3.0 — qbiq's `General!D5`=3 / `H5`=2.98 are *their* assumptions; ours is 2.6
  and it is the same number the 3D viewer builds walls at.
* `General!T9:T10` = `doors[].label` (`Glass`, `Solid`), `W9:W10` = `doors[].count`.
* One `Inventory` body row per `rooms[]` entry, same order. `Area (sqf)` = `areaM2 × 10.764`.
* **Do not re-derive any of this in TypeScript.** `takeoff.ts`'s existing wall block
  (`Drywall partition` / `Glass partition` / `Core walls`, `!generated` as the perimeter test) is a
  *different, weaker* classification and will disagree with the core on any imported DWG. It is
  still live and I did not touch it — see §6, risk 1.

### `ground_truth_json(planLabels)`

renderer (the room ids it actually drew). This module deliberately never synthesises it from its own

### `wall_types()` — for Agent C, not B3

`[{ id, wallType, planKey, lengthM }]`, where `planKey` is a `qbiqPalette.ts` `WallType`
(`'drywall' | 'half_drywall' | 'glass' | 'core' | 'perimeter_windows' | 'perimeter_wall'`).
Added because B2 left a hook for it in `wallTypes.ts` ("the day the core emits it this module stops
guessing"). Colouring the plan from this is what makes "the plan and the workbook classify the same
wall the same way" a **checked** property — there is a test
(`classify_walls_feeds_the_plan_renderer_and_reconciles_with_billing`) asserting that Σ per-type
length from `wall_types()` equals the billed per-type length, and that every `planKey` exists in
`palette.json` `plan.*`.

## 3. Classification rules — what I actually implemented

First match wins:

| # | Rule | Type |
|---|---|---|
| 1 | centreline runs along a `KeepOut` rectangle's boundary | `Core` |
| 2 | `!generated` **and** centreline runs along the traced plate polygon, `glazing` | `Perimeter windows` |
| 3 | `!generated` **and** centreline runs along the traced plate polygon | `Perimeter wall` |
| 4 | `glazing` | `Glass` |
| 5 | `height_m` set below full height | `Half Drywall` |
| 6 | otherwise | `Drywall` |

"Runs along" = all three of {start, midpoint, end} within **0.10 m** of the boundary. Sampling the
midpoint too is what stops a partition that merely *tees into* the facade being billed as facade.

### Three places I deviated from the brief's literal wording, and why

1. **`glazing == true` does NOT immediately mean `Glass`.** The brief lists that as rule 1, but also
   says a glazed boundary segment is `Perimeter windows`. Those conflict. I put the perimeter test
   first: a glazed *facade* run is `Perimeter windows` (the legend lists it separately, and qbiq's
   own `General!J11` bills 125.47 m of it), and only an *interior* glazed partition — a meeting
   room's glass front — is `Glass`.

2. **The perimeter test is geometric, not the `generated` flag.** An imported DWG has *every* wall
   `generated == false`, including interior partitions, so the flag alone would bill interior
   drywall as facade — which is what `takeoff.ts` does today. `generated` is kept only as a guard
   (the generator provably emits interior partitions only: `layout::reenclose_room` explicitly skips
   boundary edges when re-emitting a conformed room's shell), and as the **documented fallback** when
   the walls don't close so no plate can be traced. That fallback is asserted by a test
   (`open_walls_fall_back_to_the_generated_flag`) so it can't silently change.

3. **`Core` also covers keep-outs that have no modelled walls.** This is the one that would have
   silently produced a wrong number. The generator surfaces a `KeepOut` as a `Core` *zone* and emits
   **no shell walls for it at all** (`layout.rs:1922`). A pure wall-based rule therefore reports
   **0 m of core wall on every generated test-fit**. So: each keep-out contributes its own rectangle
   perimeter *unless* real walls were already classified against it — never both. Verified in both
   directions (`modelled_core_wall_replaces_the_keepout_perimeter` adds a 4 m shell wall and asserts
   Core goes to 4 m, not 18 m).

### Half Drywall — reachable, but empty on every generated plan. Stated plainly.

`Wall` had no height. I added `height_m: Option<f64>` (`serde(default)` + `skip_serializing_if`, so
pre-B1 `.dsource` snapshots load *and* an unset wall is byte-identical on the wire — the additive
guarantee `wall_flags_default_false_and_round_trip` protects; there is a matching test for the new
field). `None` = full storey height; `Some(h < 2.6)` = a half-height screen. `Editor.set_wall_height()`
is the only writer.

**Nothing in the generator or either importer ever sets it.** So on a generated test-fit
`Half Drywall` is **0.00 m**, and there is a test asserting exactly that
(`a_generated_testfit_produces_a_coherent_quantity_surface`). I did not fabricate a partition to
make the row non-empty. The category is genuinely reachable — a user or a future DWG-import pass can
set a height and the run moves into it immediately — but today it is an honest zero. (The qbiq
reference is in the same position: Agent A measured **0 pixels** of `#72BDA1` in its plan PNG, and
its `General` walls table has no Half Drywall row either.)

### Doors

Doors are `Component{category:"Door"}` and never appear in the wall list. `count` is exact,
`totalWidthM` sums `max(w, h)` per leaf. The `Glass` / `Solid` split (qbiq's `General!T9:T10`) is
**derived from the host wall**: the nearest wall within 0.6 m of the door centre — glazed → `Glass`,
else `Solid`. Not typed, not guessed from the room type.

## 4. The height assumption

**`FULL_WALL_HEIGHT_M = 2.6`**, matching `WALL_HEIGHT` in `web/src/three/Viewer3D.ts` — chosen so
the 2D takeoff and the 3D model are the same building. `Half Drywall` instead reports the
length-weighted mean of its own walls' explicit heights, so a mixed-height screen run still bills
honestly. `areaM2 == lengthM × heightM` is asserted for every row.

This is an *assumption*, not a measurement — the core carries no storey height. If the orchestrator
wants qbiq's 3.0 m / 2.98 m instead, it is a one-constant change in `model.rs`, and `quantities()`
already reports it so B3's formulas follow automatically.

## 6. Open risks

1. **`takeoff.ts` still has its own, weaker wall classification** (lines 267–303: `Perimeter wall` /
   `Perimeter windows` / `Drywall partition` / `Glass partition` / `Core walls`, using `!generated`
   as the perimeter test and zone perimeters for core). It is out of my lane and I left it running.
   If B3 wires the new sheets from `buildTakeoffModel` instead of `editor.quantities()`, the workbook
   will carry the old numbers and **G3 will fail on any imported-DWG case** (every wall is
   `!generated` there, so interior partitions get billed as facade). Recommendation: B3 replaces that
   block with `quantities()` and deletes it in the same change (no-bloat rule 2).
2. **`wallTypes.ts`'s fallback splits a perimeter run** into solid corner returns + a glazed band
   (invented 0.6 m returns) when the wall carries no `glazing`. That changes per-type totals, so it
   is a drawing convenience only. I documented it in the file and made `classifyWalls(state,
   coreTypes)` prefer the core. **Agent C must pass `editor.wall_types()`**; if the plan is coloured
   from the fallback while the workbook bills from the core, the two artefacts disagree.
3. **`rooms[]` is every zone, including `Circulation`.** That is the honest complete tiling, but
   G3 requires `Inventory` body rows == `rooms.length` exactly. If B3 filters circulation out of the
   Inventory, `ground_truth_json` must be filtered the same way — better, decide the room set once in
   the core and tell me.
4. **The 2.6 m height is an assumption** (§4), not geometry. Flagging it because it is the one number
   in this surface that isn't measured.
5. **Boundary tolerance is 0.10 m.** An imported plan with an interior partition running within
   10 cm of, and parallel to, the facade would be misclassified as `Perimeter wall`. No real plan in
   the repo triggers it; raising it would trade one error for the other.
6. **`layout::tests::real_building_plate_spreads_the_program` is flaky** — it asserts a 150 ms
   wall-clock budget on `generate()`. On this machine with three agents building concurrently it
   fails roughly one run in three. **Pre-existing, not mine**: I measured the untouched baseline
   (131 tests) and it failed 3 of 4 runs on that same test. It passes reliably at
   `--test-threads=4`. Someone should make it a non-timing assertion.
7. **Shared-worktree incident, mine, resolved.** I ran `git stash -u` to measure the baseline and it
   briefly removed B2's in-flight untracked files. On restore, two of them (`qbiqPalette.ts`,
   `wallTypes.ts`) had been rewritten by B2 in the interim; I diffed both, confirmed the on-disk
   versions were the newer ones, kept them, and dropped the stash. Nothing was lost. I have stopped
   using `git stash`/`reset`/`checkout`/`clean`/`commit` in this worktree.
