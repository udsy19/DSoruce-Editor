**Why a new viewer instead of `three/Viewer3D`** (the no-bloat one-liner, also in the file header):
`Viewer3D` is the *editor's* — it builds its own scene from a live `DocState` and carries picking,
quality tiers, minimap poses, theme persistence and an ACES/sky look. A share page loads **one baked
GLB** on a white backdrop at the *render pipeline's* settings, so the link and D's hero stills show
the same building. The substance (scene, lights, IBL, settings) is shared; only the shell is new.
**Why GLB instead of extending `export/obj.ts`:** OBJ carries no PBR materials, no texture packing
and no single-file container. Both exporters stay; neither duplicates the other.

## 2. How the share flow works end-to-end

```
Export ▸ Copy share link
  └─ publishShareLink(state)                       web/src/export/share.ts
       ├─ buildInteriorScene(state)  →  GLTFExporter(binary)     ~1.3 MB
       └─ POST /api/share/<uuid>?name=<plan>       body = the GLB
            └─ deploy/shareStore.putShare()        <PLANS_DIR>/share/<id>.{glb,json}
  └─ navigator.clipboard.writeText("https://…/share/<id>")

client opens /share/<id>
  ├─ dev  : vite middleware rewrites → viewer.html (transformed by vite)
  ├─ prod : deploy/server.ts streams dist/viewer.html
  └─ viewer.js reads the id from the URL →
       GET /api/share/<id>            → { name, createdAt } → header + <title>
       GET /api/share/<id>/model.glb  → GLTFLoader.parse → orbit/walk
```

Nothing is templated into the HTML (the page derives its own id), so the same bytes serve every
link and the file is cacheable and injection-free.

**Reproducing the artifacts** (G8 needs a running app, like G10):

```bash
pnpm --dir web dev                      # or the deploy server
node scripts/share-plan.mjs             # → out/share.json + the GLB in web/.dev-plans/share/
node scripts/gates/g8-web-viewer.mjs
```

`out/share.json` = `{"planId":"demo-seed-7","url":"http://localhost:5173/share/demo-seed-7", …}`.
`--base` flows through to the published URL, so the same script serves a VPS deploy.

## 3. The Vercel decision (documented, not accidental)

Vercel has no persistent disk, so **`/api/share/*` returns 501** exactly as `/api/plans` does
(`api/share/[[...path]].ts`). What I did *not* do is leave `/share/<id>` silently broken:

1. `vercel.json` gains `{"source": "/share/:id", "destination": "/viewer.html"}` **before** the SPA
   catch-all — without it, `/share/<id>` served the editor SPA, which would show a client the wrong
   product entirely.
2. The viewer treats **501 as a first-class state**: it stops, and says "this deployment has no
   share store — shared models are served by the full DSource server", instead of spinning forever.
3. The Export menu **falls back to downloading the `.glb`** and says so in the menu item, so a
   designer on Vercel still gets a portable, viewer-ready model in one click.

Upgrade path is one function: back `api/share/[[...path]].ts` with Vercel Blob/KV against
`deploy/shareStore.ts`'s three-call contract (`putShare` / `getShareMeta` / `getShareModel`).

**Lockstep honoured:** I did **not** put this in `apiCore.ts`. That file is the env-agnostic core for
the three proxies that *all three* targets share and it forbids fs side effects; a disk-backed store
that Vercel must refuse belongs with `/api/plans`, which already lives outside it. Instead of copying
the handler into `web/vite.config.ts` (the precedent `plansStore` set), **both servers import the same
`deploy/shareStore.ts` handler** — strictly better than lockstep-by-discipline.

## 5. Honest visual assessment — I looked at every frame

**Orbit (`out/g8-viewer.png`) — good, and it is the deliverable.** A clean doll's-house 3/4 aerial on
white: the full floorplate, perimeter curtain wall with mullions, the parquet circulation spine, the
carpeted room band, oak bench desks with monitors and chairs, the bronze/oak accent partitions, the
sage reception wall, black ring and linear luminaires, and soft contact shadows. It reads instantly as
*an office fit-out you can spin*, which is exactly what
`docs/reference/qbiq/media/Modern_revit.html` exists to do — that file is an Autodesk APS viewer shell
whose entire job is "client opens a link, spins the model". **Against that purpose we are at parity
and arguably ahead on two counts:** no Autodesk account/token/CDN is involved at all (the page is
1 same-origin HTML + 50 kB of JS + a 1.3 MB GLB), and the model arrives already dressed in the render
palette instead of raw Revit materials. Where APS is ahead: element metadata/properties on click,
sectioning, and measurement — we have none of those (see risks).

**Walk mode — works, and the spawn is deliberate.** First pass dropped the walker at the orbit
camera's plan position; on a real test-fit that put them **nose-first into a meeting-room wall** (I
have the screenshot). It now scores a 22×22 grid for open floor, spawns in the widest clear spot and
faces the longest unobstructed run — the current frame is a corridor-level view straight down the
open plan, perimeter glazing to the left, desk banks to the right. Honest defect: **above the wall
line the sky is plain white**, because the shared model omits the ceiling (§6) and the background is
white. It reads "clean render", not "inside a building".

Two defects I found by looking rather than by measuring, and fixed:
* **the canvas read back empty** (ink 0.00 %) — a WebGL canvas without `preserveDrawingBuffer` gives
  a cleared buffer to anything that reads it. The gate caught it; a client's "save image" would have too.
* **shadow acne striping across the open plan** — glTF carries no shadow flags, so my first pass set
  `castShadow` on *everything*, including the zero-thickness floor plates. Casters are now derived
  from world-box height (> 5 cm), which is what D's own scene does.

Defects I have **not** hidden: the plan is small in a very wide viewport (a rectangular plate viewed
diagonally cannot fill a 16:9 frame without clipping a corner — I chose margin over clipping); no
chairs on some desks (D-1 risk 1, a `layout.rs` truth, not a viewer bug); no shadows or reflections
from the sun outdoors since there is no exterior; and the header is the only branding — there is no
project/client block, no share expiry, no download button on the page.

## 6. Deliberate scene difference from D's stills — and its one cost

`SHARE_SCENE = { ceiling: false, exterior: false }`. A share link opens on an orbit view, and both of
those surfaces are opaque lids over exactly what the client came to see (the ceiling from above; the
300 m ground disc from anywhere). Everything else — typed walls, real door openings, perimeter
glazing, feature luminaires, palette-calibrated floors — is D's scene untouched.

**Cost:** walk mode has no ceiling overhead, hence the white sky above the wall line. The clean fix is
one line *in D's file* (`buildInteriorScene` giving the ceiling group a name, or the meshes keeping
their `userData.surface = 'ceiling'` through the exporter): the viewer could then export the ceiling
and simply hide it in orbit / show it in walk. **I did not touch `materialTheme.ts`** — it is D's lane.

## 7. Open risks

1. **The link is public and unguessable, not private.** Anyone with the id can fetch the model; there
   is no auth, expiry, or revocation. Ids are uuid4 from the app (the headless driver uses a stable
   `demo-seed-<n>` so the gate is re-runnable). Fine for a client link; **not** fine for a tenant
   boundary. Whoever adds ownership to `/api/plans` must add it here in the same change.
2. **`/api/share/:id` overwrites in place.** Re-publishing the same id replaces the model with no
   history; responses are `no-cache` so a client always sees the current one. Deliberate (a re-share
   should update, not fork), but it means a stale tab and a fresh tab can disagree mid-publish.
3. **Storage grows unbounded.** Every publish writes ~1.3 MB into `PLANS_DIR/share/` and nothing ever
   deletes it. A cleanup/TTL is not in scope here but the VPS will need it.
4. **GLB size scales with the plate.** 1.33 MB for 89 walls / 166 components at `maxTextureSize:1024`.
   A 3-4× larger floorplate is still fine over HTTP, but the store's cap is 64 MB and the app builds
   the whole thing in the main thread — a very large plan will stall the UI for a few seconds
   (the menu item shows "Publishing 3D model…" throughout, so it is at least legible).
5. **No BVH, no LOD, 12 point lights.** The viewer renders the whole scene every frame with the full
   light rig (down from D's 28 luminaires for a realtime budget). On a phone or a software
   rasterizer this will be slow; there is no quality tier and no `powerPreference` fallback.
6. **`preserveDrawingBuffer: true`** costs a little fill-rate on every frame. Accepted so the canvas
   can be read back (screenshots, and the gate's ink test).
7. **G10's one click does not yet produce `out/share.json`.** The pack action
   (`exportDeliverablePack`) is client-side and does not publish. `publishShareLink(state, {name})` is
   a one-line call and returns exactly `{planId, url}` — wiring it into the pack is the orchestrator's
   call, not mine, since it changes `qtoWorkbook.ts` (another lane).
8. **Root `tsc -p tsconfig.json` reports 3 pre-existing errors** in `web/src/editor/EditorCanvas.ts`
   (`import.meta.env` needs vite's client types), reachable from `apiCore.ts`'s existing import chain.
   Not mine and not new — `deploy/shareStore.ts` and `api/share/*` themselves compile clean under the
   root config (I installed the root devDeps to check; `pnpm-lock.yaml` unchanged).
