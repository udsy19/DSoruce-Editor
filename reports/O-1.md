# O-1 — Room-Type Truth: one derivation, every sheet

**Agent O.** Fixes E4 (`defects-2.md`): the workbook told two stories about one Room ID —
**Reception was billed as a "Kitchen"** on `Furniture Inventory` while the `Inventory` sheet for the
same Room ID said "Reception". Also closes K-1 §9.1, the `zoneAtPoint` follow-up K left in my lane.

**Headline: 18 of 18 billed rooms now agree across sheets — 0 contradictions, read out of the shipped
`.xlsx` itself.** One mapping deleted, none added.

---

## 1. The canonical source I chose

**`finishSchedule.ts::roomTypeLabel(zone)`** — a three-line function over the vocabulary that was
*already* canonical (`finishTypeFor` + `TYPE_LABEL`, which the `Inventory` sheet has always read).

```ts
export function roomTypeLabel(z: DocZone | null): string {
  if (!z) return TYPE_LABEL.other
  if (z.zone_type === 'Circulation') return 'Circulation'
  return TYPE_LABEL[finishTypeFor(z)]
}
```

**Why this and not `ZoneType`, and not a field on `planRoomList`:**

* **`ZoneType` is too coarse to be the answer.** It has 7 values; the plan has 16 distinguishable room
  types. Reception, Pantry, Print Point, Storage, Wellness and IT/Server are *all* `Amenity` zones —
  that is precisely why the deleted table mapped `Amenity → 'Kitchen'` and billed the reception desk's
  chair under a kitchen. `ZoneType` is already published, honestly, as the Inventory's **Space Type**
  column ("Amenity"); the fine-grained type is **Subcategory**, and `finishTypeFor` is what produces it.
* **`planRoomList` is the canonical room SET, but it cannot host the type.** `planGraphic.ts`'s module
  graph pulls in the 3D viewer (`sheetSet → section → sectionRender → Viewer3D → furniture3d`, which
  builds a canvas texture at import time — B3-1 §4). `takeoff.ts` is deliberately DOM-free so
  `takeoff.test.mjs` can bundle it for Node; making it import `planGraphic` would have broken that.
  `finishSchedule.ts` is DOM-free at import, so `takeoff.ts` can read it — verified, the Node bundle
  builds and runs.
* `roomTypeLabel` is **not a third mapping.** It is the single entry point onto the existing one, and
  it absorbed the only special case that used to be written out by hand (`qtoWorkbook.ts`'s inline
  `pr.zoneId == null ? 'Circulation' : …`), which is now gone too.

**Three consumers, one call.** `Inventory!Subcategory`, `Furniture Inventory!Room Type` (via
`takeoff.ts`) and the drawing set's Room Finish Schedule `ROOM TYPE` column are now the *same call on
the same zone*. A fourth consumer was fixed for free: `sheetSet.ts::buildMoodGroups` groups the
moodboard by `r.roomType`, so the PDF's moodboard headings and its finish schedule now use one
vocabulary (they previously read "Kitchen" and "Reception" in the same document).

## 3. `zoneAtPoint` — K-1 §9.1, agreement made structural

`takeoff.ts::zoneAtPoint` took the **first** containing zone. K fixed `Document::zone_index_at` to
prefer a non-`Circulation` zone and then the **smallest-area** one, and flagged that the TS side only
agreed with it "by emission order, not by rule" — rooms happen to be emitted before the plate-spanning
Workspace field, so first-wins landed on the room by luck. `zoneAtPoint` now implements the core's
rule line for line (specific beats Circulation; within a class, smallest area wins).

This is what makes the `Furniture Elements` column (TS bucketing) and the `Headcount` column (core
bucketing) provably the same answer — the D8 failure mode K closed in the core, closed on the TS side
too. Callers: `zoneFor` (the BOM) and `App.tsx::buildRoomRefs` (marker → zone), both of which want the
most specific room, and both of which now get it by rule.

## 5. The regression guard — test **and** gate-visible

**(a) Unit assertions** (`takeoff.test.mjs`). The old check only asserted the room type was one of
seven hard-coded strings — it would have passed with Reception billed as a Kitchen for ever. Replaced
with an *agreement* check that bundles `finishSchedule.ts` through its **own** esbuild entry point, so
it compares two independently-built modules rather than a value with itself:

* Room Type ∈ the one canonical vocabulary (`TYPE_LABEL` ∪ `Circulation`)
* `Furniture Inventory` Room Type **===** `Inventory` Subcategory for every billed room, printing each
  disagreement
* an explicit "a Reception room is NOT billed as a Kitchen"
* three `zoneAtPoint` cases on nested synthetic zones (smallest wins / specific beats Circulation /
  Circulation as fallback) + every component agreeing with the core's own `component_ids` bucketing

**(b) Gate-visible tripwire** (`qtoWorkbook.ts::assertOneRoomType`). `scripts/gates/**` is Agent M's
lane, so I could not add a gate check — instead `buildQtoModel` **throws** if any Room ID carries two
different types. That fails the export itself, so every gate that runs through `buildQtoPack`
(G1/G2/G3/G5/G9/G10) and the in-app Export ▸ Quantity Takeoff click both surface it. Rows whose Room
ID has no Inventory row (the `"OS"` catch-all) are skipped — nothing to contradict.

**Both were proven discriminating** by re-introducing each defect in `takeoff.ts` and re-running
(then reverting immediately — I ran no `git` mutation of any kind):

## 7. Notes / follow-ups (not mine to fix)

1. **The `"OS"` Room ID has no Inventory row.** On the `dwg` case one furniture row is billed to Room
   ID `"OS"` — the catch-all for a component whose centre lies outside every zone. It now reads
   `Other` (inside the one vocabulary) instead of the old free-floating `Open Space`, and my tripwire
   correctly skips it, but a reviewer reading the two sheets still finds a Room ID on one sheet and not
   the other. The real fix is upstream — either the imported plate should carry a zone there, or those
   components should be dropped from the BoQ like `reference` ones are. Pre-existing; not in scope.
2. **`Inventory!Space Type` is still the coarse `ZoneType`** ("Amenity" for Reception, Pantry, Print
   Point, Storage, Wellness, IT/Server). That is correct — it is the *department-level* column and it
   comes from the core's `quantities()`; Subcategory is the fine-grained one. No action, recorded so
   nobody "fixes" it into a third mapping.
3. **No gate compares the two sheets.** `g1-sheet-structure.py` reads the `Furniture Inventory` headers
   only; `g3-quantity-truth.py` never touches that sheet. Whoever owns `scripts/gates/**` could turn
   §5(b)'s invariant into a handful of real G3 checks by reading `Furniture Inventory!D/E` against
   `Inventory!G/F`. Until then the throw in `buildQtoModel` is what makes it gate-visible.
4. I touched no Rust. `crates/ds-core` was in my lane but needed no change — the core's bucketing rule
   was already right (K's fix); the TS side was the one that had drifted.
