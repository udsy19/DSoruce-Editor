**Follow-up to `reports/B1-1.md`. Lane: `crates/ds-core/**` + the ground-truth section of
`web/src/export/qtoWorkbook.ts`. Nothing in Agent D's lane touched.**

**Outcome: I took the DELETE branch, not the preferred branch.** Reasoning, evidence and the
verification that nothing regressed are below. Short version: the core *cannot* own
`ground-truth.json`, and making it own only the room set would have created a second copy of the

I was asked to fix, and with a live risk of regressing G4/G5.

### What replaced the deleted tests' coverage

The two deleted tests asserted (a) the emitted JSON's camelCase key shape and (b) that
`plan_labels` was passed through rather than synthesised. Both were about a JSON emitter that no
longer exists, and both are now covered *more strongly*, on the real artifact, by G3 — which checks
the required keys, the wall keys against `General!J*`, door counts against `General!T/W`, the sqf
arithmetic, and the 1:1 plan-label correspondence.

What did NOT transfer is the core's ownership of the **key vocabulary**: the strings `"Drywall"`,
`"Half Drywall"`, `"Perimeter windows"` … are defined by `WallType::label()` in the core, and G3
matches them by exact string. So I added one replacement test, `ground_truth_key_vocabulary_is_pinned`,
which pins the six wall labels and two door labels in order, asserts they are unique (a collision
would silently drop a row from the ground truth's `walls` object), and re-pins the sqf factor. Net
test count: **−2 +1**.

## 2. Why the core cannot own `ground-truth.json`

This is the load-bearing part of the report, so it is evidence, not assertion.

### 2.1 The ground-truth room record is not a geometry record

`ground-truth.schema.json` defines `rooms[]` with `floorMaterial` ("Must match a `General!B9:B*`
Material Name"), `ceilingMaterial`, `subcategory`, `department` and `furnitureElements`
(`"{Item Description}: {qty}, ..."`). Reading `qtoWorkbook.ts::buildQtoModel`, those come from:

| Field | Source | In the core? |
|---|---|---|
| `floorMaterial`, `ceilingMaterial` | `FINISH_SPEC` / `finishTypeFor` (`finishSchedule.ts`) | **no** — 16 room types × India-market finishes, TS-only |
| `subcategory` | `TYPE_LABEL` (`finishSchedule.ts`) | **no** |
| `furnitureElements` | `buildTakeoffModel` (`takeoff.ts`) | **no** — furniture descriptions + bank bindings |
| `roomId` | `opts.roomRefs` overriding the zone id | **no** — CAD room-marker map, held TS-side |
| `planLabels` | the plan renderer's draw output | **no** — Agent C |
| `renders` | Agent D, merged post-hoc by `scripts/render-rooms.mjs` | **no** |
| walls · doors · areas · sqf factor | `Editor.quantities()` | **yes** — and already used verbatim |

A core-side emitter can only produce the last row. Everything above it would have to be dropped or
re-invented in Rust.

### 2.2 A core emitter would *reintroduce* the divergence G3 exists to detect

This is the decisive point. G3's whole job is to prove that three independently-produced sets — the
Inventory rows, the ground-truth rooms, and the plan labels — are identical. Today all three descend
from a single call to `planRoomList`, so the check passes *by construction*.

If the core emitted the ground truth, its room set would be computed independently of the one the
Inventory sheet is written from. Even if I ported the rule faithfully, the two implementations could
drift on the next change to either side, and G3 would then be passing on a coincidence rather than
on a structural guarantee. Handing the gate a second opinion to compare against its own is the
opposite of what it is for.

### 2.3 The preferred fix cannot be completed inside my lane without duplicating the rule

The room-set rule lives in `planGraphic.ts::planRoomList` (Agent C's file, explicitly out of my
lane). It returns, per room, an id **and a label position** — `zoneCenter` of the zone, or of the
largest circulation zone for the aggregated `"0"` row — because the plan renderer needs somewhere to
draw the label.

To move selection into the core I would have to either:

* **leave `planRoomList` in place** → the rule then exists in Rust *and* in TS. Two copies of a
  business rule where there is currently one. That is a worse no-bloat violation than the dead
  function I was sent to remove; or
* **edit `planGraphic.ts`** to consume the core list → out of lane, and it would need the core to
  reproduce `zoneCenter` for all three `ZoneShape` variants (including a true `Poly` centroid). Any
  disagreement between my Rust centroid and the TS one moves labels on the plan PNG, which is
  precisely what **G4** (plan graphic, currently PASS, 14 checks) and **G5** (thumbnails, PASS, 70
  checks) measure.

Given the standing instruction that the seven green gates must not regress, spending that risk to
end up with the rule written twice was not a trade worth making.

### 2.4 Where the CLAUDE.md concern actually lands

"Never put document/business logic in the TS renderer" is the right instinct, and it is worth being
precise about what remains in TS after this change:

* **Wall classification, door typing, room areas, headcount, the sqf factor** — all in the core, and
  `takeoff.ts`'s old weaker wall classification was already replaced by B3 (its wall block is gone;
  `takeoff.test.mjs` now asserts against `Editor.quantities()`).
* **What zones are schedulable rooms** (`NON_ROOM_ZONES = {Circulation, Core}` + one aggregated
  `Room ID "0"`) — still in `planGraphic.ts`, in **exactly one place**, consumed by the renderer,
  the Inventory and the ground truth alike.

That last rule is not really document logic: it is a *reporting convention* of this particular
deliverable (it exists to mirror the reference workbook's row 35), and it is inseparable from label
placement. It has one definition and three consumers. I think that is the correct home for it, but
it is a judgement call, so §4 records what it would take to move it if the orchestrator disagrees.

## 4. If you want the room set in the core anyway

I'll do it, but it needs a lane change and one decision, because it cannot be done well in
`crates/ds-core` alone:

1. Add `quantity::inventory_rooms(doc, room_refs) -> Vec<InventoryRoom>` carrying `room_id`
   (`String`, `"0"` for the aggregate), `zone_id: Option<u32>`, area, headcount, **and a centroid**
   for label placement. Expose it on `quantities()`.
2. Give me `web/src/export/planGraphic.ts` so `planRoomList` becomes a thin adapter over it and the
   rule keeps exactly one definition. Without this step the rule ends up written twice and I would
   rather not do it at all.
3. Accept that `ground-truth.json` still gets assembled in `qtoWorkbook.ts`, because
   `floorMaterial` / `ceilingMaterial` / `furnitureElements` / `subcategory` are unavoidably TS-side
   (§2.1) — unless you also want the finish schedule ported into Rust, which is a much larger job
   and would pull India-market pricing data into the geometry crate.
4. Budget for a G4/G5 re-verify: step 1 makes the core compute zone centroids, and if a `Poly`
   centroid differs from `zoneGeom.ts::zoneCenter` the plan labels move.

My recommendation is to leave it as it is now. The deliverable currently has one definition of the
room set, one definition of wall classification (the core), and no dead code — which I think is the
state the two rules were aiming at.

## 5. Risks

1. **`quantities().rooms` is still per-zone, including `Circulation` and `Core`.** That is correct
   for its actual job (it is the per-zone area/headcount lookup table `buildQtoModel` joins against,
   and the source of the aggregated circulation sum), but the name invites the misreading that it is
   the Inventory row set. I documented the distinction in the `quantity.rs` module header and in
   `buildQtoGroundTruth`'s doc comment; a future agent should read those before wiring a new
   consumer.
2. **`Perimeter windows` is 0.00 m on all three exported cases.** Not caused by this change and not
   a bug in the classifier — no plate wall in those documents carries `glazing: true`, so every
   facade run correctly bills as `Perimeter wall`. It does mean the deliverable currently shows a
   glass-free facade. If that is wrong for the product, the fix is upstream (the generator/importer
   should mark facade glazing), not in the classifier. Flagging because the reference workbook bills
   125.47 m of perimeter windows and a reviewer comparing side by side will notice.
3. **`Half Drywall` remains 0.00 m** on every case, as reported in B1-1 §3 — still honest, still
   unreachable from any generator or importer path.
